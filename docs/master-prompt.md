# 네이버 블로그 자동화 대시보드 — 마스터 프롬프트

> 이 문서는 실제로 완성된 "네이버 블로그 자동화 대시보드" 프로젝트의 요구사항을
> 하나의 프롬프트로 정리한 것입니다. Claude Code에게 새 프로젝트로 처음부터
> 붙여넣어도 될 만큼 구체적으로 썼습니다. 강의에서 그대로 활용하셔도 됩니다.

---

## 이 프롬프트를 그대로 쓰면 한 번에 다 될까? (강의에 꼭 넣으면 좋은 내용)

**부분적으로 맞고, 부분적으로는 아닙니다.** 정확히 말씀드릴게요.

- **맞는 부분**: "무엇을 만들 것인가"(기능/규칙/데이터 구조)를 처음부터 이렇게
  구체적으로 던져주면, "이것도 해줘", "저것도 빠졌네" 하는 왔다갔다가 확실히
  줄어듭니다. 실제로 이 프롬프트에 들어있는 내용의 80% 이상은 실제 대화에서
  여러 차례에 걸쳐 요청했던 것들인데, 처음부터 이렇게 정리해서 줬다면 그 왕복은
  안 해도 됐을 내용입니다.
- **아닌 부분**: 이 프로젝트에서 실제로 시간이 걸렸던 문제들 상당수는 **프롬프트
  품질과 무관하게, 실제로 화면을 띄워서 눌러보기 전에는 알 수 없는 것들**이었습니다.
  - 네이버 에디터의 실제 DOM 구조/버튼 위치는 문서화되어 있지 않아서, 실제
    로그인된 브라우저를 열어 직접 눌러보며 셀렉터를 확인해야 했습니다.
  - "무료 이미지인 줄 알고 클릭했는데 사실 유료라 결제 팝업이 뜨고 전체 화면을
    막아버리는" 것 같은 함정은 실제로 겪어보기 전에는 예측 불가능했습니다.
  - 체크박스를 눌러도 반응이 없던 버그, 유효성 검사 오류가 화면에 안 뜨던 버그는
    라이브러리 버전 궁합 문제였고, 실제 사용자(강사님)가 클릭해보고 알려주기
    전에는 코드만 봐서는 드러나지 않았습니다.
  - **한 번 만들어 놓으면 끝이 아닙니다.** 완성해서 잘 쓰던 중에 네이버가 로그인
    후 착지하는 페이지를 조용히 바꿔서, 로그인이 아예 완료되지 않는 상태가 된
    적이 있습니다. 내 코드는 한 줄도 안 건드렸는데 어느 날 갑자기 안 되는 거죠.
    외부 서비스를 자동화하는 프로젝트는 **상대가 바뀌면 같이 고쳐야 하는 유지보수
    비용이 계속 든다**는 점을 수강생에게 미리 알려주시면 좋습니다.

  **결론: 이런 종류의 프롬프트는 "왔다갔다의 횟수"는 확실히 줄여주지만, "왔다갔다
  자체가 0번"이 되지는 않습니다.** 특히 네이버처럼 실제 외부 서비스 화면을
  자동으로 조작해야 하는 프로젝트는 라이브 테스트 없이는 완성될 수 없다는 점을
  강의에서 꼭 짚어주시면 좋을 것 같습니다. (반대로, 순수하게 코드/로직만으로
  끝나는 작업이라면 이런 프롬프트 한 방으로 훨씬 더 근접하게 끝납니다.)

## 1. 프로젝트 개요

로컬 PC에서 실행되는, 네이버 블로그에 학원/업체 블로그 글을 올리는 과정을
**반자동화**하는 대시보드를 만들어줘. 핵심 철학은 "AI가 글을 쓰고 화면에 채워
넣는 것까지는 자동, 그러나 로그인과 최종 발행 버튼은 반드시 사람이 직접"이야.

**절대 원칙 (타협 불가):**
- 네이버 로그인은 반드시 실제로 보이는 브라우저 창에서 **사람이 직접** 아이디/
  비밀번호를 입력해야 해. 자동화 코드가 로그인 폼에 값을 채우는 코드는 어디에도
  있으면 안 돼.
- **발행(게시) 버튼은 자동화가 절대 클릭하면 안 돼.** 자동입력이 끝나면 브라우저
  창을 열어둔 채로 멈추고, 사람이 내용을 확인한 뒤 직접 발행 버튼을 눌러야 해.
  이 규칙은 코드 리뷰로만 지키는 게 아니라 **구조적으로** 강제하고 싶어 —
  예약(스케줄러) 관련 코드가 발행 자동화 코드를 아예 import할 수 없도록
  정적 분석 도구(dependency-cruiser 등)로 빌드 단계에서 막아줘.
- AI 글쓰기는 유료 API 키가 아니라 **로컬에 이미 로그인된 Claude Code 구독을
  재사용**하는 방식으로 만들어줘 (Claude Agent SDK의 `query()` 사용, 서버
  프로세스에 `ANTHROPIC_API_KEY`가 설정되어 있으면 오히려 에러를 던지도록
  방어 코드를 넣어줘).

## 2. 데이터 모델 / 업체 정보

업체 정보는 한 번만 입력해두면 모든 글에 자동으로 재사용되는 싱글턴으로 저장:
업체명, 주소, 강점/특징, 참고사항, **인사말**(매 글 첫 문장 고정), **네이버 톡톡
URL**, **네이버 예약 링크**, **주소 링크**(네이버 지도/플레이스 URL — 글 하단에
"오시는 길"로 붙는 링크), **내 말투 샘플**(예전에 직접 쓴 블로그 글 원문을
붙여넣으면 AI가 문체를 참고), **해시태그 세트**(매 글 끝에 고정 삽입).

"주소"와 "주소 링크"는 다른 필드야. 앞의 것은 AI 프롬프트에 넣는 사람이 읽는
주소 문자열이고, 뒤의 것은 글에 실제로 삽입할 지도 링크야 — 한 필드로 합치지 마.

### 2-1. 글 종류별 첨부 요소 대시보드

같은 화면에 **홍보성/정보성 × 톡톡·예약·주소** 6칸짜리 체크박스 표를 만들어줘.
체크한 항목만 그 종류의 글 하단에 링크로 붙는다. 기본값은 홍보성 = 톡톡+예약 켬,
정보성 = 전부 끔, 주소는 양쪽 다 끔.

> **왜 설정으로 뺐는지:** 처음엔 "정보성 글에는 판매 냄새가 나는 링크를 절대
> 안 붙인다"를 코드에 하드코딩했는데, 실제로 운영해보니 "정보성에도 오시는 길
> 정도는 붙이고 싶다"는 요구가 나왔어. 종류별로 다르게 가져가고 싶은 건 맞지만
> 그 판단은 코드가 아니라 운영자가 해야 하는 것이었어. 처음부터 설정으로 만들되
> **기본값을 위와 같이** 두면, 코드에 박아둔 것과 똑같이 동작하면서 나중에 바꿀
> 여지가 남아.

체크가 켜져 있어도 해당 URL이 비어 있으면 아무것도 삽입하지 마 (빈 링크를 넣지
말고 그냥 생략). 그 상태를 대시보드에서 경고로 알려주면 더 좋아.

## 3. 글 종류: 홍보성 vs 정보성

두 가지 글 종류를 지원해줘. 성격이 완전히 다르니 프롬프트도, 조립 규칙도 따로
가져가야 해.

**두 종류를 한 화면에서 쓰게 해줘.** 글쓰기 폼 맨 위에 "글 종류" 라디오를 두고,
고른 값에 따라 아래 입력칸이 바뀌는 방식(홍보성이면 제목 입력칸, 정보성이면 그
칸이 사라지고 주제 키워드). 화면/메뉴 이름도 **"글 작성"** 처럼 종류를 가리지
않는 이름으로 해줘 — "홍보글 작성"이라고 붙였더니 실제 사용자가 "정보성 글은
어디서 쓰냐"고 한참 찾은 일이 있었어. 라디오가 폼 안에 있어서 눈에 안 띄었던 거야.

### 3-1. 홍보성 글
- 사용자가 **제목을 직접 입력**하고, 그 제목은 AI가 절대 바꾸지 않고 그대로 써.
- 타겟 키워드(선택)를 본문에 정확히 4번 자연스럽게 등장시켜.
- 분량은 공백 포함 2500~3200자.
- 구조: 서론 5~6문단 → 소제목 3~4개(소제목당 문단 8~10개) → 결론 4~5문단.
- 과장 광고 문구, 근거 없는 최상급 표현("최고", "1등" 등)은 금지. 업체 정보에
  없는 구체적 사실(수상 경력, 통계 등)은 절대 지어내지 마.
- 인사말 → 톡톡 안내 → (AI 본문) → 직접 써놓은 내용(있다면) → 예약 안내 →
  주소(오시는 길) 안내 → 관련 글 링크(비워두면 최근 발행글로 자동 연결) →
  해시태그, 이 순서로 코드가 고정 조립해줘 (AI는 본문만 씀). 톡톡·예약·주소
  세 가지는 2-1의 대시보드 설정에 따라 붙거나 빠져.
- 예약과 주소를 **둘 다** 붙일 때는 예약 쪽 문구에서 "오시는 길"을 빼줘
  ("예약/오시는 길 안내" → "예약 안내"). 안 그러면 바로 아래 주소 링크와 같은
  말을 두 번 하게 돼.
- 관련 글 링크는 홍보성 전용이고 대시보드 대상이 아니야 — 업체 정보가 아니라
  글 쓸 때마다 입력하는 값이라 성격이 달라.
- **예약 안내는 "장소/지도 위젯"이 아니라, 등록해둔 예약 URL을 그냥 텍스트로
  입력하는 방식으로 만들어줘.** 처음엔 "장소" 위젯(업체명으로 검색해서 지도
  카드를 넣는 기능)을 썼는데, 이건 실제 예약 URL과 무관한 일반 주소 카드만
  보여줘서 "예약 링크를 넣었는데 안 나온다"는 문제로 이어졌어. 실제 예약
  URL(`booking.naver.com/...`)을 텍스트로 그냥 입력하면 네이버가 자동으로 그
  예약 페이지 자체의 미리보기 카드(사진+소개글)로 확장해주는 걸 라이브로
  확인했어 — 지도 위젯보다 이게 훨씬 정확하고 유용해.

### 3-2. 정보성 글
- 사용자는 **주제 키워드만** 입력하고, **AI가 클릭을 유도하는 제목을 직접 지어**.
  실제 본문과 내용이 일치해야 하고 낚시성 거짓말은 안 돼.
- 홈피드(추천 피드) 노출을 노리는 콘텐츠라서, 다음 6가지 스타일을 반드시 지켜:
  1. 도입부(5~6문단)는 실제 사건/이슈를 기반으로 시작해서 최소 2문단 이상 상황을
     설명한 뒤, 글쓴이(원장)의 개인적 반응을 자연스럽게 삽입.
  2. 소제목은 **정확히 3개**만, 단순 요약형이 아니라 클릭을 유도하는 "문장형"
     제목으로 (질문/반전/의외의 주장 등 댓글을 부르는 장치 포함).
  3. 글 전체에 걸쳐 글쓴이의 경험/주관적 해석이 **최소 4번 이상** 등장.
  4. 정보와 감정이 교차하는 리듬, 대화체 기반의 자연스러운 흐름.
  5. "충격", "반드시" 같은 정형화된 클릭베이트 표현은 피하고 실제 사람이 수다
     떨듯 자연스럽게.
  6. 결론(4~5문단)은 댓글/공감을 유도하는 열린 질문으로 마무리.
- 분량은 2200~3200자. 인사말과 해시태그는 항상 붙고, 관련 글 링크는 붙이지 마.
  톡톡/예약/주소는 2-1 대시보드 설정을 따르되 **기본값은 전부 끔** — 홈피드
  노출을 노리는 글이라 영업 색이 짙어지면 역효과라는 판단이야. 운영자가 필요하면
  켤 수 있게만 열어두고, 처음 상태는 아무것도 안 붙은 채로 시작해줘.

### 3-3. 공통 규칙
- **말투는 반드시 정중한 존댓말(해요체/합쇼체)**로 써. "~입니다", "~에요",
  "~랍니다", "~까요?"처럼 끝나야 하고, "~있다", "~한다"처럼 끝나는 반말은 단
  한 문장도 쓰면 안 돼. (이 규칙을 안 넣으면 AI가 "정보성"이라는 지시를 "편하게
  써도 된다"로 오해해서 갑자기 반말을 섞어 쓰는 문제가 실제로 있었어 — 대화체
  지시와 반말 금지를 같이, 명시적으로 넣어줘.)
- 등록해둔 "내 말투 샘플"이 있으면 문체(어미, 리듬)만 참고하고 내용을 베끼지는
  말라고 명시해줘.
- 사실관계(통계/트렌드 등)를 다룰 때는 WebSearch 도구로 검증한 뒤, 검색한 문장을
  그대로 베끼지 말고 완전히 자기 말로 다시 풀어써야 해. 출처 URL이나 다른
  블로거 이름은 본문에 적지 마.
- **최근에 이미 쓴 같은 종류의 글과 소재/각도가 겹치지 않도록**, 최근 발행/작성된
  글 제목과 요약을 프롬프트에 함께 넣어서 AI가 피해가도록 해줘.
- 인라인 서식: `**굵게**`, `==노란 형광펜==`, `__밑줄__` 마크업을 본문에서 쓰게
  하고, 실제 네이버 에디터에 채워 넣을 때 이 마크업을 해당 서식으로 변환해줘.
- 사진 자리 3개, 영상 자리 2개, 이모티콘 자리 2개, 구분선 4개를 본문 안에
  적절히 배치하도록 AI에게 시켜줘.

## 4. 사진은 자동으로 넣지 마 (직접 넣는 게 최종 결론)

사진/영상 자리는 사용자가 직접 파일을 업로드한 경우에만 채우고, **업로드된
파일이 없으면 그냥 건너뛰고 경고 로그만 남겨줘.** 자동으로 사진을 찾아 넣는
기능은 만들지 마.

> **강의용 참고 — 왜 이 결론에 도달했는지:** 처음에는 "네이버 에디터 안의
> 무료 이미지 검색(글감 검색 → 이미지 카테고리 → 무료 라이선스 필터)을 써서
> 사진 자리를 자동으로 채우면 어떨까" 하고 실제로 만들어봤어. 라이브로
> 확인해보니 기능 자체는 있었지만(무료/유료 필터도 있었음), 실사용 중
> 반복적으로 자동입력이 멈추는 문제가 있었어 — 유료 이미지를 잘못 클릭하면
> 전체 화면을 덮는 결제 팝업이 뜨고, 이미지 검색 패널이 열려있는 동안 투명한
> 오버레이가 다른 버튼 클릭까지 막아버렸거든. 재시도/복구 로직까지 짜서
> 라이브로 검증까지 마쳤는데도, 실제 사용자가 반복 사용해보니 여전히 가끔
> 멈췄어. 결국 "이 정도 리스크를 감수할 가치가 없다, 사진은 내가 직접 넣는
> 게 낫다"는 게 실제 결론이었어. **이 프로젝트를 처음부터 다시 만든다면 이
> 기능 자체를 아예 시도하지 말고 사람이 직접 넣는 것으로 시작하는 걸
> 추천해** — "일단 만들어보고 아니면 되돌린다"도 정상적인 개발 과정이라는
> 걸 보여주는 좋은 사례이긴 하지만, 시간을 아끼고 싶다면 처음부터 이 프롬프트
> 대로 "자동 삽입 없음"으로 가는 게 나아.

## 5. 초안 검토 화면

AI가 쓴 글은 바로 발행 대기가 아니라 "검토 대기" 상태로 저장하고, 사람이 화면에서
블록 단위로 확인할 수 있게 해줘. 사진/영상 자리에는 직접 파일을 업로드할 수 있는
UI, 링크 블록은 직접 수정 가능하게, 확인 후 "승인" 버튼으로 다음 단계(에디터
자동입력)로 넘어가게 해줘. 글자수/키워드 등장 횟수가 목표 범위를 벗어나면
경고를 화면에 표시해줘 (자체 재시도를 몇 번 해보고도 안 맞으면 가장 근접한
초안을 채택하고 경고만 남겨줘 — 무한 재시도는 하지 마).

**자동입력을 한 번 한 글도 "에디터에 다시 열기"로 다시 채울 수 있게 해줘.**
처음엔 자동입력이 끝나면 상태가 "발행 대기"로 넘어가면서 그 버튼이 사라지게
만들었는데, 그날 에디터 창을 닫았거나 발행을 미루면 그 글은 다시 열 방법이
아예 없어서 그대로 묶여버려 (실제로 이렇게 묶인 글이 쌓여서 "버리고 새로 쓰는
수밖에 없나" 하는 상황이 됐어). 서버 쪽은 상태 제한을 두지 말고, 화면에서만
버튼 문구를 바꿔 보여주면 돼. 다시 열면 빈 글쓰기 화면에 처음부터 새로 채운다는
점(네이버에 남은 임시저장을 이어쓰지 않는다는 점)을 버튼 옆에 안내해줘.

## 6. 네이버 로그인 & 에디터 자동입력

- Playwright + Edge(`channel: 'msedge'`, 번들 Chromium 아님)로 실제 브라우저
  창을 띄우고, 로그인은 그 창에서 사람이 직접. 로그인 자체는 `NID_SES` 쿠키가
  생기는지 폴링해서 판정하고, 세션(storageState)을 저장해서 다음부터는 로그인
  없이 재사용. 저장된 세션이 서버에서 보기엔 있는데 실제로는 만료된 경우를
  감지해서 자동으로 재로그인 흐름으로 안내해줘.
- **내 blogId는 `https://blog.naver.com/MyBlog.naver`로 이동한 뒤 도착한 주소
  (`blog.naver.com/<blogId>`)에서 읽어줘.** 예전에는 `blog.naver.com/`이 로그인한
  사람의 블로그로 리다이렉트해줬는데, 지금은 남의 글이 뜨는 홈피드
  (`section.blog.naver.com/BlogHome.naver`)로 보내. 거기엔 내 blogId가 어디에도
  없어서, 이걸 모르고 만들면 **로그인은 성공하는데 blogId를 못 찾아 세션이 저장되지
  않고, 아무리 로그인해도 화면엔 계속 "로그인 안 됨"으로 남는** 상태가 돼 (실제로
  겪었고 원인 찾는 데 한참 걸렸어).
- blogId는 **페이지 주소에서만** 뽑고, **HTML을 뒤져서 `blog.naver.com/<아이디>`
  형태의 링크를 긁는 방식은 절대 쓰지 마.** 홈피드 HTML에는 모르는 사람들의 블로그
  링크가 가득해서, 그걸 긁으면 **남의 블로그를 운영자 것으로 저장**해버릴 수 있어.
  (`?blogId=` 쿼리 형태를 보조로 쓰더라도 `blog.naver.com` 도메인에 있을 때만.)
- 이런 종류의 리다이렉트 주소는 네이버 DOM만큼이나 문서화돼 있지 않고 예고 없이
  바뀌어. 로그인 흐름에는 셀렉터가 없어서 "여긴 안 깨지겠지" 하고 방심하기 쉬운데
  똑같이 깨져 — 저장된 세션으로 브라우저를 띄워 후보 주소들을 실제로 방문해보고
  어디에 도착하는지 찍어보는 진단 스크립트를 먼저 돌린 뒤에 구현해줘.
- 승인된 초안을 실제 네이버 에디터 화면에 사람처럼 타이핑해서 채워 넣어줘
  (제목 → 본문 블록 순서대로, 서식은 블록 직전에 켜고 직후에 꺼서 다음 블록에
  안 새어나가게). 진행 상황은 실시간 로그(SSE)로 화면에 보여줘.
- **채워 넣기가 끝나면 그대로 창을 열어두고 멈춰** — 사람이 자유롭게 더 고치거나
  사진을 추가한 뒤 직접 발행하도록.

## 7. 예약(스케줄러)

- cron 기반으로 요일·시각을 지정해 "글감 준비 → AI 초안 작성"을 자동 실행할 수
  있게 해줘. **PC(서버)가 그 시각에 켜져 있어야만 실행된다**는 제약은 화면에
  분명히 안내해줘 (꺼져 있으면 그냥 건너뛰고, 나중에 자동으로 만회 실행되지
  않음 — 놓친 건 "지금 실행" 버튼으로 사람이 직접 채우게).
- 예약마다 **글 종류(홍보성/정보성)를 복수 선택** 가능하게 해줘 — 둘 다 선택하면
  실행될 때마다 홍보성↔정보성을 **정확히 번갈아(라운드로빈)** 발행하도록. (무작위가
  아니라 순서대로 교대해야 "주 4회, 2+2로 섞어서" 같은 요구가 정확히 맞아떨어져.)
- **글감을 어떻게 정할지 두 가지 모드**:
  - "고정 주제": 실행될 때마다 매번 똑같은 제목/키워드 (딱 1개 글 종류를 골랐을
    때만 의미 있음 — 2개를 고르면 이 모드는 막아줘).
  - "글감 큐 사용": 아래 "글감 메모장"에서 그 실행의 글 종류에 맞는 글감을 오래된
    순으로 하나씩 꺼내 쓰고, 큐가 비면 AI가 최근 글과 안 겹치는 새 주제(정보성)
    또는 완성된 제목(홍보성)을 스스로 지어서 씀.
- 예약이 실행되고 나면(성공/실패/타임아웃 어느 쪽이든) **카카오톡 "나에게
  보내기"로 결과를 알려주는 기능**을 선택적으로 붙여줘. 사업자 인증이 필요 없는
  개인 카카오 개발자 앱의 REST API 키만 있으면 되는 방식으로 — 사용자가 카카오
  개발자 사이트에서 앱을 만들고, "카카오 로그인" 활성화 후 대시보드에서
  "카카오 연결하기"를 눌러 실제 카카오 로그인 화면에서 본인이 직접 동의하는
  흐름으로 (비밀번호는 이 프로그램을 절대 거치지 않아야 해). 알림 발송이
  실패해도 실제 글 생성 결과에는 영향이 없도록 완전히 분리해줘.

## 8. 글감 메모장

생각날 때마다 글감을 적어두는 공간을 만들어줘. **홍보성/정보성을 나눠서
등록**하고 (홍보성 글감은 그대로 글 제목으로 쓰이고, 정보성 글감은 AI가 주제로
삼아 제목을 새로 지음), 예약이 소비하면 사용 여부를 표시해줘 (사용된 것도 이력은
남겨서 보이게).

## 9. 발행 이력 & 관련 글 자동 연결

발행은 사람이 직접 하지만, "발행완료로 표시" 기능은 만들어줘 (Playwright를
전혀 쓰지 않는 순수 DB 기록 — URL만 입력받아 저장). 홍보성 글의 "관련 글 링크"를
비워두면 가장 최근에 발행완료 표시된 글로 자동 연결해줘.

**여기서 끝내면 발행 이력이 영원히 비어 있게 돼.** URL을 손으로 붙여넣는 기능만
만들면, 그 전제("지금 발행했으니 주소가 있다")가 실제 사용 방식과 안 맞아서야:

- 실제로는 에디터에서 **네이버 자체의 예약 발행**을 걸고 창을 닫는 경우가 훨씬
  많아. 그 시점엔 글이 아직 없으니 **붙여넣을 주소 자체가 존재하지 않아.**
- 며칠 뒤 실제로 발행되고 나면, 대시보드로 돌아와 주소를 붙일 이유를 잊어버려.
- 그래서 "발행 대기"만 계속 쌓이고 발행 이력은 0건이 돼 (실제로 이렇게 됐어).

그러니 **블로그를 읽어서 자동으로 맞춰주는 기능**을 같이 만들어줘:

- 블로그 공개 RSS(`https://rss.blog.naver.com/<blogId>.xml`, 최근 50개 정도
  내려옴)를 읽어서, "발행 대기" 상태 글과 **제목이 같은 글**을 찾으면 그 주소를
  발행 완료로 기록. 로그인도 Playwright도 필요 없어서 브라우저 큐와 무관하게
  아무 때나 돌릴 수 있어.
- 제목이 그대로면 정확히 일치로 보고, 앞부분(20자 정도)만 겹쳐도 같은 글로 봐줘 —
  블로그 주인이 제목 뒤에 키워드를 덧붙이는 일이 잦거든. 다만 짧은 제목에서
  엉뚱한 글이 걸리지 않게 최소 길이를 두고, 앞부분만으로 맞춘 건 화면에 "주소를
  한번 확인해주세요"라고 표시해줘.
- 못 찾은 글은 건드리지 말고 발행 대기에 그대로 둬 (정말 아직 발행 전인 경우).
- **버튼 하나로 끝내지 말고, 앱이 켜져 있는 동안 1시간마다 자동으로도 돌려줘.**
  버튼만 있으면 "발행되고 나서 버튼 누르는 걸 기억해야" 하니 원래 문제가 그대로
  남아. 자동 확인은 조용히 돌아야 해 — 기록한 게 있을 때만 로그를 남기고, 실패
  (로그인 전/네트워크 문제/블로그 무응답)는 경고 한 줄로 끝내고 다음 주기를
  기다려. 타이머는 `unref()` 해서 이것 때문에 프로세스가 안 죽는 일이 없게.

## 10. 기술 스택 / 구조 제안

- npm workspaces: `shared`(zod 스키마 공유) / `server`(Express + better-sqlite3
  + Playwright) / `web`(React + Vite + react-query + react-hook-form).
- react-hook-form에서 zod 스키마로 유효성 검사를 붙일 때는 라이브러리 버전
  궁합을 꼭 실제로 테스트해봐 — `@hookform/resolvers`와 zod 버전이 안 맞으면
  **검증은 정확히 실패해서 제출이 막히는데, 에러 메시지가 화면에 하나도 안
  뜨는** 버그가 날 수 있어 (버튼이 멀쩡해 보이는데 눌러도 아무 반응이 없는
  것처럼 느껴짐). 의심되면 resolver 없이 `schema.safeParse()` +
  `setError()`로 직접 검증하는 게 오히려 안전해.
- 체크박스/라디오를 커스텀 UI로 만들 때, `<input checked onChange>`가 네이티브
  기본 동작(클릭 시 자동 토글)에만 의존하게 두면 실사용자 클릭에서 반응이
  없다는 버그가 날 수 있어 (텍스트 라벨 클릭 시 미세한 마우스 움직임을 브라우저가
  "텍스트 선택"으로 오인해서 클릭 자체가 씹히는 경우가 실제로 있었음). `<label>`의
  onClick에서 직접 상태를 바꾸고 `preventDefault()`로 브라우저 기본 동작은 막는
  방식이 더 안전해.
- **실시간 로그(SSE)를 "요청은 202로 즉시 응답하고 작업은 뒤에서 시작"하는
  방식으로 만들 거면, 초반에 바로 실패하는 경우를 조심해줘.** 클라이언트는 202를
  받은 *뒤에야* 로그 스트림을 구독하는데, 그 사이에 작업이 실패해서 메시지를
  publish하면 듣는 사람이 아직 없어. `EventEmitter`는 버퍼가 없어서 그 메시지는
  큐에 쌓이지 않고 그냥 사라지고, 이후 구독한 화면은 영원히 빈 로그만 보게 돼 —
  **버튼을 눌러도 아무 일도 안 일어나는 것처럼 보이는** 최악의 증상이야 (실제로
  "로그인 안 된 상태에서 자동입력" 케이스에서 겪었고, 원인을 두 번 헤맸어).
  실행 전에 확인할 수 있는 조건(로그인 여부 등)은 **202를 주기 전에 미리 검사해서
  HTTP 에러 + 사람이 읽을 메시지로 돌려줘.** API 래퍼도 응답 본문의 `message`를
  그대로 에러 문구로 쓰게 해두면 화면에 바로 뜨고, 근본적으로는 로그 버스에
  runId별 버퍼를 두는 게 맞아.
- Windows에서 `concurrently`로 여러 워크스페이스를 동시 실행하면 `tsx watch`
  프로세스의 출력이 먹통이 되는 경우가 있었어 — 문제가 생기면 직접 만든 간단한
  오케스트레이터 스크립트(`node child_process.spawn`)로 바꾸는 것도 방법이야.
- zod로 "부분 수정"(PATCH) 검증을 만들 때 두 가지를 조심해줘: (1) 필드 간
  교차검증(`superRefine`)이 걸린 스키마에는 `.partial()`을 호출할 수 없어
  (zod v4 기준 에러 던짐) — PATCH용으로는 `superRefine` 적용 *전*의 순수
  객체 스키마를 따로 만들어서 그걸 `.partial()`하도록. (2) `.partial()`로
  각 필드를 선택적으로 만들어도, 값을 안 보낸(undefined) 필드에 대해 zod가
  `.default(...)`를 계속 적용해버려 — 그래서 "필드 하나만 바꾸려고" 보낸
  요청인데 나머지 필드가 전부 스키마 기본값으로 조용히 덮어써지는 심각한
  버그로 이어질 수 있어(실제로 겪음: 활성화 체크박스만 껐다 켰는데 예약의
  다른 설정이 몰래 초기화됨). PATCH 핸들러는 파싱된 결과 전체를 병합하지
  말고, **요청 바디에 실제로 들어있던 키만 골라서** 기존 값 위에 덮어써야 해.

## 11. 검증 방식 (강의에서 꼭 강조)

이 프로젝트의 기능 대부분은 **실제 로그인된 브라우저를 띄워서 라이브로
확인**하며 완성했어. 코드만 보고 "맞겠지"라고 넘어간 부분에서 실제로 버그가
났고 (형광펜 토글, 유료 이미지 함정, 체크박스 클릭, 유효성 검사 등), 라이브
테스트를 안 했다면 발견하지 못했을 문제들이야. 새 기능을 붙일 때마다:
1. 진단용 스크립트로 실제 화면/DOM을 열어서 구조를 확인하고,
2. 구현한 뒤 실제로 눌러보고,
3. 문제가 생기면 다시 진단 → 수정 → 재확인,
이 사이클을 도는 걸 기본 워크플로우로 삼아줘.
